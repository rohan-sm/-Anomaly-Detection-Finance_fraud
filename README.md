# Financial Fraud / Anomaly Detection API

This project is a **fraud detection system** that identifies **anomalous financial transactions** using **unsupervised machine learning**, specifically **Isolation Forest**, and exposes predictions through a **FastAPI REST API**.

The focus of this project is on **real-world fraud behavior modeling**, clean backend design, and explainable predictions — not just model accuracy.

---

## 🔍 Problem Statement

In real financial systems:
- Fraud is **rare and highly imbalanced**
- Labels are often **missing or delayed**
- Fraud patterns change over time

Because of this, treating fraud detection as a **supervised classification problem** is often unreliable.

➡️ This project approaches fraud as an **anomaly detection problem**, where transactions that deviate strongly from normal user behavior are flagged as potential fraud.

### 📦 Why the generated `data/` is committed

The 100,000-row dataset is **fully synthetic** — generated by
`src/data_generation/` from a fixed seed (`RANDOM_SEED = 42`), with no real
customers, no real card numbers, and no licensed or sensitive source data
anywhere in its provenance.

That makes committing it harmless and useful:

* **Anyone can clone and reproduce** — every metric in `reports/` and the
  README can be regenerated and independently verified, with no dataset
  download, no Kaggle account, and no data-sharing bottleneck.
* **No privacy or licensing risk** — there is nothing here that could leak a real
  transaction or cardholder.
* **Reviewers can evaluate the modelling immediately** rather than reconstructing
  the data first.

`python run_pipeline.py` regenerates it deterministically, so the committed
files serve as a fixed reference point: if a regeneration ever diverges from
what is checked in, that divergence is a real bug rather than an environment
difference.

The trade-off is repository size (~94 MB), which is a deliberate and acceptable
cost for a self-contained, reproducible project.

## 🤖 Models Used

Three unsupervised models were trained on the same 9-feature matrix and the same
scaler, then compared at matched operating points.

| Model | Configuration | Ranking ROC-AUC | F1 @ 1% flag rate |
|-------|---------------|-----------------|-------------------|
| **Isolation Forest** | 300 trees, contamination 0.01, seed 42 | **0.5991** | **0.0608** |
| Autoencoder | 9→64→32→64→9, 5,417 params, Adam 1e-3, MSE | 0.5925 | 0.0520 |
| One-Class SVM | RBF kernel, nu 0.01, gamma scale, 1,086 SVs | 0.5226 | 0.0412 |

**Isolation Forest ships as the primary model** because it has the best F1 and
ROC-AUC, trains in ~4s, and emits a usable ranking score.

The other two are kept as **complementary signals** rather than discarded: the
autoencoder captures non-linear structure the forest's axis-aligned splits miss,
while the One-Class SVM's ROC-AUC of 0.52 (near random) is itself the finding —
fraud is not separable by a single global boundary, because legitimate users are
highly heterogeneous.

> **Honest framing:** an ROC-AUC of 0.60 means the model ranks *somewhat* better
> than random. The defensible claim is not "high accuracy" but **5.97× precision
> lift over the 1.038% base rate** at a 1% alert rate, plus a systematic
> three-way comparison and a contamination sweep that quantifies the
> precision/recall trade-off (recall 6% → 20% as flags go 1% → 10%).

## 📊 Feature Engineering Philosophy

Fraud is rarely about raw values.
It’s about **contextual deviation**.

### The 9 Features Actually Used
| Feature | Why It Matters |
|------|---------------|
| `amount_dev_log` | Signed-log deviation from the customer's own 24h baseline |
| `avg_amount_24h` | Personal spending baseline (fraud is relative, not absolute) |
| `txn_count_1h` | Burst / card-testing velocity attacks |
| `txn_count_24h` | Daily spending intensity |
| `time_since_last_txn_sec` | Time since last transaction — small gaps are suspicious |
| `distance_from_home` | Geographic deviation from the customer's home |
| `travel_speed_kmh` | Impossible travel, capped at 20,000 km/h |
| `hour_sin` / `hour_cos` | Cyclical time-of-day encoding (no 23:00→00:00 cliff) |

Identity and label columns (`customer_id`, `merchant_id`, `card_number`,
`merchant_category`, raw lat/long, `is_fraud`, `fraud_type`) are dropped before
modelling — see the drop audit in `notebooks/01_data_validation.ipynb`.

⚠️ **Same preprocessing pipeline is used during training and inference**
  (`build_features()` is imported by both the batch job and the API), so there is
  no training–serving skew.

## 🧠 Why Isolation Forest?

Multiple anomaly detection approaches were experimented with during development.

**Isolation Forest was chosen for the final system because:**
- It performed **most consistently** on validation data
- It scales well to large transaction volumes
- It works naturally with **tabular financial features**
- It provides a clear anomaly score that can be converted into a fraud probability

Rather than overengineering, the final system uses **one strong, explainable model**.

## 🔮 API Endpoints

### `POST /predict`

Scores a single transaction.

#### Request
```json
{
  "customer_id": "CUST_00042",
  "amount": 45000.0,
  "timestamp": "2025-02-14T03:10:00",
  "hour": 3,
  "distance_from_home": 980.0
}
```

#### Response
```json
{
  "fraud_score": -0.099,
  "fraud_probability": 0.2709,
  "is_fraud": false,
  "risk_level": "LOW",
  "contributing_factors": [
    { "feature": "distance_from_home", "value": 980.0, "z_score": 3.516, "direction": "above_normal" },
    { "feature": "avg_amount_24h",     "value": 45.0,  "z_score": -1.333, "direction": "below_normal" },
    { "feature": "hour_cos",           "value": 0.7071,"z_score": 1.005,  "direction": "above_normal" }
  ],
  "explanation": "Transaction sits inside the normal behavioural range. Closest signals: distance_from_home=980.0 (z=+3.5), ..."
}
```

| Field | Meaning |
|-------|---------|
| `fraud_score` | Raw Isolation Forest score, **higher = more anomalous** |
| `fraud_probability` | Signed distance from the threshold mapped through a steep sigmoid, so the threshold sits exactly at 0.5 |
| `is_fraud` | `fraud_probability >= 0.5` |
| `risk_level` | `HIGH` ≥ 0.8 · `MEDIUM` ≥ 0.5 · else `LOW` |
| `contributing_factors` | Top 3 features ranked by how far they sit from the population the model was fitted on |

**About `contributing_factors`:** Isolation Forest has no native additive
attribution, so `z_score` is each feature's distance in standard deviations from
the training scaler's mean — not a Shapley value. It answers "which inputs
dragged this transaction out of the normal region", which is what a risk analyst
needs. For features where only an increase is anomalous (`txn_count_*`,
`distance_from_home`, `travel_speed_kmh`, `time_since_last_txn_sec`) a value far
*below* normal is correctly treated as unremarkable.

### `POST /batch_predict`

Same scoring, up to 1,000 transactions in one vectorised pass. Returns
`count`, `flagged`, `flag_rate`, `mean_fraud_probability` and a `predictions`
list in **submission order**.

### `GET /` and `GET /health`

Liveness / readiness probes.

## 🧮 Fraud Probability Logic

Isolation Forest outputs an anomaly score, not a probability. The signed distance
from the configured threshold is passed through a steep sigmoid:

```
margin = score - threshold
probability = 1 / (1 + exp(-10 * margin))
```

Because the threshold maps to exactly 0.5, `is_fraud = probability >= 0.5` is
always consistent with the score's own decision boundary — the probability and
the decision can never disagree. The steepness (10) makes the transition sharp
rather than smearing probabilities across the whole 0–1 range.

This keeps the decision logic:
* Simple
* Transparent
* Easy to explain in interviews

## ▶️ Running the Application

```bash
pip install -r requirements.txt

# Run the API
uvicorn app.main:app --reload

# Run the full pipeline end to end
python run_pipeline.py                      # generate -> features -> train -> evaluate
python run_pipeline.py --stage train        # retrain only (~4s, seeded)
python run_pipeline.py --stage evaluate     # contamination sweep -> reports/
python run_pipeline.py --stage train --contamination 0.05

# Run the tests
pytest -q                                  # 35 tests
```

Training is seeded, so re-running reproduces the committed artifacts
(`precision 0.0620 / recall 0.0597 / F1 0.0608 / ranking ROC-AUC 0.5991`,
confusion matrix `[[98024, 938], [976, 62]]`).

## ⚠️ Known Limitations

Stated plainly, because they are the interesting part of the system:

1. **The API is stateless.** Rolling features (`avg_amount_24h`, `txn_count_1h`,
   `time_since_last_txn_sec`) are computed from whatever history is present. On a
   single-shot request that means `amount_dev_log` and `travel_speed_kmh` are
   always 0, so a ₹45,000 transaction at 3 AM from 980 km away scores *low*. The
   batch pipeline reconstructs these correctly; serving does not. Fixing this
   needs a feature store (Redis) or a persisted per-customer baseline.
2. **Metrics are modest.** ROC-AUC 0.599 is real signal but far from a strong
   classifier. The lift over base rate, not raw accuracy, is the honest result.
3. **Synthetic labels.** Fraud is injected by three deterministic rules, so the
   model is partly learning the rules that generated the labels. This validates
   the pipeline and the serving path, not real-world detection power.
4. **Merchant collusion is only ~97 cases.** Too few for that class to be
   reliably detectable at a 1% threshold.
